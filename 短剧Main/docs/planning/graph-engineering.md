# 图工程:平台自迭代的回路网络

> 立于 2026-07-28,DC 指定方向(参考 eigent.ai《Graph Engineering for AI Agents》)。
> 核心主张:**一个反馈回路只是一块积木,不是整个系统。要设计的是一张回路网络——
> 让它们互相监视、互相约束、互相纠正,而不是各自安静地偏离现实。**

## 一、四层回路(谁在纠正谁)

| 层 | 回路 | 谁跑 | 周期 | 产出 |
| --- | --- | --- | --- | --- |
| **执行** | 任务包 → worktree → 交付三件套 | kimi(前端)/ sol(后端难档)/ terra(普通档) | 分钟~小时 | 代码 + 回执 + tag |
| **质量** | 验收实操:变异验证 / 真渲染 / 真 PG 端到端 / 边界核对 | opus5 | 每包一次 | 验收回执(通过/带条件/打回) |
| **治理** | 拆包、裁决、合流、迁移号分配、排期 | Fable | 每轮心跳 | orchestration.md / version-plan.md 回写 |
| **审计** | 指标是否还对应真实结果:执行人质量盘点、真源新鲜度、"界面上摸得着"复核 | opus5(定期)+ DC(随时) | 天~周 | 盘点报告 / 判决单 |

## 二、边(约束关系,不只是流向)

- **质量回路对执行回路有否决权**:验收打回 = 该包不得合流。执行人自报不算数(三件套 + 变异)。
- **治理回路设定质量回路的判据**:任务包必须提前公布考法(变异点、真点到路径);公布了不执行,比不公布更糟(护栏 `plan-freshness` 会红)。
- **审计回路可以推翻治理回路的判断**:S86 盘点明确区分「执行人的锅」与「Fable 任务包写法的锅」——7 条判给了 Fable。**审计不许只审下层。**
- **快回路不得改写自己的目标**:心跳可以执行、验收、合流、派包,**不得**改 `version-plan.md` 的档期与卡片、不得改 `dc-verdicts.md` 的判决、不得放宽门禁。要改就升级给 DC。
- **升级而非覆盖**:任何需要拍板/授权的事,停在只读态,给 DC 选择题。

## 三、锚定(防自指漂移)

内部检查全绿但系统已脱离现实,是这套东西最危险的失效模式。四个**不可被自我编辑**的外部锚:

1. **DC 的眼睛** —— 审美与产品体验的终审。技术验收通过 ≠ 定版通过(S79 就是这么处理的)。
2. **真实运行** —— 真 PG 端到端、浏览器真点到、真后端响应。「源码里搜得到」不是证据。
3. **真源文件** —— `version-plan.md`(做什么)、`dc-verdicts.md`(DC 说过什么)、`orchestration.md`(现在到哪)。由 Fable 单写,执行人只读。
4. **门禁数字三件套** —— 总数 / 通过 / skip。只报「0 失败」是骗人的,skip 不是中性的。

配套的**反向指标**(防止单指标被优化到失真):

| 主指标 | 反向指标 | 为什么配对 |
| --- | --- | --- |
| 合流包数 | 验收打回率 / 返工率 | 只冲数量会降质量 |
| 门禁通过数 | skip 数 + 变异咬合率 | 绿灯可能是纸糊的 |
| 交付速度 | 「界面上摸得着」的变化 | 后台忙碌不等于用户获益 |
| 任务包数 | 每包 DC 决策等待时长 | 派得多不等于推进快 |

## 四、节奏分离(慢的约束快的)

- **心跳(30 分钟)**:判活、验收、合流、补派、上报。战术层,不动战略。
- **版本档(天~周)**:一档收口一次,更新 plane 与版本计划。
- **版本计划(周~月)**:DC 拍方向、定优先级、重排档期。

**慢层的决定,快层不能推翻**。心跳发现某卡不该做,写进上报,由 DC 在计划层改。

## 五、已知的失效模式(都真发生过,不是假设)

- **代理指标冒充验证**:数用例名、数测试总数、读自己写的笔记、拿 fake 跑通——全不算。
- **绿灯掩护**:真实保护躺在 skip 里,默认门禁一条都不红(S61 二轮复核实证)。
- **回执漏报比虚报更贵**:执行人说真话时同样会漏,而且漏得更严重(S67 在途单风险、S79 三个 token)。
- **心跳制造虚假忙碌**:「每轮都要有产出」的压力会催生新包、新文档,而不是回头核旧账。**没有变化就一句话带过。**
- **审计只审下层**:把 Fable 的任务包缺陷算到执行人头上,会导致换人换 effort 都无效。
