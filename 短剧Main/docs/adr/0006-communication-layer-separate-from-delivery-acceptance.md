# ADR-0006:会话间通信的「已处理」只是通信语义,唤醒护栏装在收件方

- 日期:2026-08-18
- 状态:已接受(DC 拍板)
- 决策人:DC;梳理:Fable

## 背景

`delivery-workflow.md` 新增「十五、会话间通信」,把 agent 会话之间递条子、交报告、报阻塞写进真源。定稿前按 dc-ground-rules 6c 过了蜂群审计:四家独立评审(DeepSeek、豆包、Kimi、通义,走 COL 通道)给 3、3、4、4 分,匿名互驳一轮后两家下调、两家维持,无人上调。五个最重问题被四家逐条重合点出。

其中两处不是文字问题,是定义问题,四家意见分裂,需要拍板:

**其一:「已处理」要不要门禁证据。** 一家主张,处理完成必须以门禁结果、系统回执、复验通过记录为准,否则就突破了「自报不作数」的证据纪律。另三家反驳:这混淆了两个层次,通信层的「已处理」只回答「这条消息被读取并处置了」,活干得对不对自有双首长制和复验线管;收件方日志是**系统可观测痕迹**,不等于 worker 口头自报。

**其二:唤醒护栏装在哪一侧。** 一家主张,发 `reply_expected: true` 的件时由发信方负责确认收件方存活并唤起。另一家反驳:这只是把断点从收件方挪到发信方,发信方同样可能发完即闲置,仍然无解。

## 决策

**「已处理」限定为通信语义,与交付验收分开。**

- 它表示这条消息被收件方读取并处置,判据是收件方自己的日志或回信;
- 它**不代表**活干对了。交付是否合格仍归双首长制与复验线,不因一条回执视为验收。

**唤醒护栏装在收件方,做成准入条件。**

- 合格收件方 = 配了自动收信的会话。没配的会话不得被指定为汇报对象;
- `blocked` 不是终点:必须同时落到对应正式载体并计超时,只回发信方不算数。

**通道只投递,效力由既有载体产生。** 结论经通道送达、落正式载体之后才生效,不得仅凭一条消息生效。

## 考虑过的其他做法

**让「已处理」绑定门禁与复验证据。** 好处是口径最严,坏处是通信层再也无法独立成立——一条「我收到了」的回执要等复验通过才能确认,通道退化成交付流程的附属品,报阻塞这类高时效场景直接失效。四家中三家反对,采纳多数。

**发信方负责确认存活并唤起。** 好处是发信方最清楚自己等谁,坏处是发信方本身也可能是短命 agent,发完即闲置,断点只是换了个位置。护栏装在会一直存在的一侧(收件方配置)才闭合。

**推倒重写整节。** 一家主张定性为「体系性架空既有全部治理机制」。另三家反驳:新增内容没有明文废止任何既有路径,真正的问题是缺映射造成旁路。按 3 比 1 取补章。

## 后果

- 第十五节新增「消息类别 → 正式载体 → 记到哪本账」映射表,以及权限判定顺序(先查第四节,触上会/DC 的一律不得自决);
- `autonomy` 字段的效力被限定在「线内自决」范围内,它不能把一件事降级;
- 没配自动收信的会话不能被当作汇报对象,这会在指定汇报关系时形成一道检查;
- 对不产生会话日志的 Harness(Claude Code、Codex),「已处理」拿不到日志级证据,只能靠回信关联——这是已知缺口,记在该节 Limitations。

## 不在本决议范围内

消息传输的实现(命令、路径、传输层行为、已知 bug)属 `agent-session-communication` skill,工具会变、判据不变,不进真源。

用共享任务表 + 显式任务状态替代「靠消息互相催」是另一条路线,已记在 `dario-github/coding-environment` issue 156,本决议不预判它。
