# ADR-0002:模型 provider 分层,为将来的国内/海外剥离预留

- 日期:2026-07-28
- 状态:已接受(DC 拍板)
- 决策人:DC;架构:Fable

## 背景

兄弟团队闪灵(FlareFlow)的产品需求要接**海外 provider**:ElevenLabs(配音/音效/BGM)、
gemini-3.1-pro 与 gpt-5.4(文本创意)。我们现有的生成链全部走火山 Ark
(seedream 图片 / seedance 视频 / doubao 文本与向量)。

DC 定调:
> 「兄弟团队的参考,我们把他们需求支持了,他们的导演才会用我们产品。」
> 「内部使用,没有合规义务。**对外时再把海外 API 和国内 API 剥离,面向不同用户。**」

也就是说:**现在可以接海外 provider,但将来必须能按用户群切换**。

## 决策

**从接入第一个海外 provider 起,就按「provider 可按用户群切换」的形状设计,不做事后重构。**

具体三条:

1. **provider 选择是运行期决策,不是编译期常量。** 具体用哪家由「用户所属群 + 能力类型」解析得出,
   不许在业务代码里写死厂商名或模型 ID(这条同时是硬编码盘点 S74 的既有结论:模型 ID 与单价进配置)。
2. **能力抽象按「能做什么」命名,不按厂商命名。** 例:配音能力叫 `voice-synthesis`,
   不叫 `elevenlabs-tts`;它下面挂哪些 provider 是配置。
3. **计费与成本账本按 provider 记录来源**(承 S84 供应商成本账本,迁移 038),
   剥离时才能按用户群算清各自的成本。

## 为什么现在做

**成本不对称**:现在做只是「命名与一层解析」,几乎零成本;等两条产品线跑起来再剥离就是重构,
而且要动已经在花钱的流程——本仓最不愿意动的地方。

**已有同型教训**:同一个 `GET /projects/:id/costs` 被两处按不同契约实现、前端只跟了一边,
消耗页对用户报「请求内容不正确」,查了整整一轮才定位(`outputs/opus-8080-cost-page-diagnosis-20260728.md`)。
provider 若在业务代码里散落写死,将来剥离会同型重演,而且更贵。

## 合规边界(重要,别误读)

DC 的「内部使用,没有合规义务」**仅适用于当前内部阶段**。
我们已查实的三层义务(AIGC 标识、广电编码、算法备案,底稿在 `outputs/`)**在对外那一刻恢复适用**,
而且**海外 provider 的产物在国内对外分发时,标识与备案义务不会因为模型在海外而豁免**。

因此:
- **对外开放前必须完成国内/海外剥离**,这是上线的前置条件,不是优化项;
- 剥离方案与合规底稿一起复核后才可对外;
- 本 ADR 不构成「海外 provider 可用于对外服务」的结论。

## 后果

**得到的**:接兄弟团队需求不欠架构债;将来按用户群切换是配置动作不是重构;成本可按 provider 分摊。

**付出的**:每接一个新 provider 多一层抽象成本;能力命名要先想清楚(不能图快用厂商名)。

**约束(后续包必须遵守)**:
- 业务代码里出现厂商名或具体模型 ID = 打回;
- 新增能力先定能力名与参数形状,再挂 provider;
- 成本记录必须带 provider 标识,否则剥离时算不清账。
