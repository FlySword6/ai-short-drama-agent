# ADR-0004:test 分支只做 dev 的下游,不接受原生提交

- 日期:2026-08-12
- 状态:已接受(DC 拍板)
- 决策人:DC;梳理:Fable

## 背景

| `43f378c7` `0346b644` `68906bbc` `423ddad3` `3685cb78` `5ac65eda` `8d8f2207` `5136f7c3` `3405625b` | CI/构建/Docker(火山 CR runtime base、npm 缓存、VKE checkout 信任、Playwright 退场换固定 chromium) |

关键判断:这 9 个 CI 提交在**当时是合理的**。火山流水线跑不通,而彼时 dev 已领先 test 一批未在 test 环境验证的改动,走 `merge dev into test` 会把一次「改一行 CI」放大成一次大合流,风险更高。直接在 test 上修是理性选择。

真正的问题不是「在 test 上修」,是**修完没有回流 dev**。而且这不是一次手滑:`43f378c7` 夹在两次 `Merge dev into test` 中间,说明直接改 test 是常规动作,当事人当时并不觉得自己在违规——因为从来没有一条规矩说过不行。

## 决策

**`test` 是 `dev` 的纯下游。`dev` 在 patch 层面恒为 `test` 的超集。**

正常情况下,`test` 上只应出现 `Merge dev into test` 这一种提交。不再制造 `release(test):` 空提交——发版 tag 直接打在对应的 merge 提交上,发版锚点一点不少,还省掉一个人造提交。

唯一例外是 hotfix,两条硬线同时满足才算:

1. `test` 环境**当前是坏的**(不是「将要坏」,也不是「有点慢」);
2. 修复只碰 CI、构建、配置,**不碰产品代码**。碰产品代码的,不管多急都走正常 dev→test。

hotfix 的做法是:**在 `dev` 上修,再把那一个提交 cherry-pick 到 `test`**。这样 `test` 上会出现一个原生 SHA,但它的内容在 `dev` 上有等价补丁,`dev` 依然是超集,同时避免把 `dev` 上未验证的改动整批拖进 `test`。

守卫按 **patch 等价**判,不按 SHA 可达判:push 到 `test` 的每个新提交,要么是 merge 提交,要么 `git cherry origin/dev origin/test` 认为它在 `dev` 上有等价补丁,否则 CI 红。

### 判据的边界:squash 合并会改掉 patch-id

**回流 `dev` 的 PR 不能用 squash 合并。** 这是对 `CONTRIBUTING.md` §二.5「squash 合并」的明确例外。

`git cherry` 按 patch-id 比对。squash 把 N 个提交压成 1 个,合并后那个提交的 patch-id 跟原来 N 个都不相等,于是原提交会继续被判成「未回流」——门禁永远不转绿。

这不是推测,是 #298 自己撞出来的:门禁那个 PR 以 squash 合进 `dev` 之后,对它原来的两个提交跑判据,仍然判 `+`,而文件明明已经在 `dev` 上了。

危险在于第二步反应:门禁报红而人确信「东西已经合进去了」,最省事的做法就是往豁免名单里加两条。**名单一旦开始因为「判据不准」而变长,这道门就废了。** 所以宁可在合并方式上开一个明确的例外,也不让豁免名单变成默认静音开关。

规范用法下撞不到这条:hotfix 是「在 `dev` 上修,再把**已经合进 `dev` 的那个提交** cherry-pick 到 `test`」,两边都是单个提交,patch-id 一致。撞得到的是「把一个 PR 里的多个原始提交 cherry-pick 过去,而该 PR 在 `dev` 侧是 squash 合的」。

## 考虑过的其他做法

**hotfix 从 test 切分支,合回 test 的同时也合进 dev。** test 上会多出一个合 hotfix 分支的 merge 提交,守卫得放宽成「要么是 merge、要么在 dev 可达」。漏合 dev 那边守卫能抓住,但要求每次记得合两遍,多一个出错口子。

**hotfix 一律带着 dev 的全部改动一起过。** 只有 `dev` 恒定保持可发布状态才成立。`dev` 目前天天在动,不成立。

**只写进文档、靠人守。** 这已经是惯犯了,`43f378c7` 就是在两次正常合流中间顺手改的。文档拦不住一个不觉得自己在违规的人。

## 后果

买到的:`dev` 在 patch 层面恒为超集,今天这种「一批提交无处可归」的账不会再有;发版可以从 `dev` 切,不用担心 `test` 上藏着 `dev` 没有的东西。

付出的:hotfix 多一跳。测试环境挂了不能直接在 `test` 上按一刀,得先在 `dev` 上修再 cherry-pick 过去。cherry-pick 有撞冲突的可能,但 hotfix 按定义就该是小改,概率低。

规矩管以后,不追认过去:

- `test` 分支历史**不改写**,不 force push。已有的原生提交留在那儿,下次正常 `dev` → `test` 合流时内容自然收敛。
- `v0.2.2` tag **不挪**。它现在指着 `43a8e3cb` 那个空提交;为了历史干净去动一个已推到远端的 tag,风险和收益不成比例。自本决议起改用「tag 直接打在 merge 提交上」。

## 不在本决议范围内

`origin/main` 落后 `origin/test` 1519 个提交,停在 2026-07-25,既不是生产真源也不是集成基线。这笔烂账单独立案。

context 仓的 `docs/specs/spec-sdlc-map.md` 停在 2026-07-04,它对 `CONTRIBUTING.md` 的评价已经不作数(见上面的订正框)。整份图谱该按现状重扫一遍,同样单独立案——本决议只在 `CONTRIBUTING.md` 里补了 `test` 分支纪律那一节。
