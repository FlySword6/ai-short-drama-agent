# ADR-0001:流水线由画布引擎渲染(长期归一)

- 日期:2026-07-28
- 状态:已接受(DC 拍板)
- 决策人:DC;架构:Fable

## 背景

产品有两种创作界面形态:

- **流水线(Pipeline)**:现有工作台,「项目→集→分镜→媒体」的结构化生产流程。我们替用户搭好的路,上手门槛低。
- **画布(Canvas)**:节点式自由创作空间,节点可以是文本、生成任务、资产引用,连线表达数据流。自由度最高、门槛也最高。

DC 2026-07-28 定调:**流水线是画布的一个预制模板(a workflow),关系单向——流水线可以「打开为画布」,画布不能转回流水线。**

定调之后剩一个没答的问题:两者是**同一套代码**,还是**两套并行只共享后端数据**?

## 决策

**长期归一:画布引擎是底座,流水线是「预置布局 + 锁定交互」的画布。**

不是立刻重写。分两步:
1. 画布 MVP 阶段就把引擎层与业务层分开——几何/结构操作(平移、缩放、吸附、分组、连线)是纯函数,节点内容是普通 React 组件;
2. 流水线在后续版本逐步迁到该引擎上渲染,迁一块拆一块,不推倒重写。

## 备选方案与为什么没选

**两套并行,只共享后端实体。** 短期最快:流水线代码一行不动,画布另起炉灶。

否掉的理由是**功能会被实现两遍,并且悄悄长歪**。这不是假设——本仓已经吃过同型的亏:同一个 `GET /projects/:id/costs` 被 dashboard 与 operations 两处按不同契约实现,前端只跟了一边,结果消耗页对用户报「请求内容不正确」,查了整整一轮才定位(见 `outputs/opus-8080-cost-page-diagnosis-20260728.md`)。界面层若也分家,同样的事会在「生成节点在画布里和在工作台里行为不一致」上重演,而且更难查——因为两边各自的测试都是绿的。

**先不定,MVP 出来再说。** 否掉的理由是归一成本随代码量单调上涨,而这个决策现在做几乎零成本(只是要求 MVP 分层),拖到画布铺开后再做就是重写。

## 后果

**得到的:**
- 一个功能实现一次,两种形态自动一致;
- 「流水线打开为画布」是同一份渲染树换一套布局约束,不是数据导出+重建;
- 新交互(多人协同光标、节点级评论、版本快照)做一次两边都有。

**付出的:**
- 画布 MVP 要多做一层引擎/业务分离,估计晚一到两个包;
- 流水线迁移期会有一段「一半旧代码一半新引擎」的中间态,必须有守卫测试盯住两边行为一致,否则迁移期就是缺陷高发期。

**约束(后续包必须遵守):**
- 画布引擎层不许知道「分镜」「集」这些业务概念,业务语义只能在节点组件里;
- 几何与结构操作必须是纯函数(承接 `docs/design/canvas-v030-principles.md` 已立的三条原则);
- 画布**不得**成为绕过报价确认的第二条生成通道——生成一律走既有 `generation` 模块的报价→确认→消费链,不新增生成端点。
