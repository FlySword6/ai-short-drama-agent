## 三、发版列车制(Release Train)

**原则:版本号是全家桶的,不是单仓的。** 每次发版=一列车,四仓同名 tag
(vX.Y.Z),车长=Fable,发车即全链一致。

1. **车次定义**:下一车=**v0.2.0**(内容=0.2.0+0.2.x 增量波的验收门:
   公网可登录可生成可审核可交付+审核/交付门禁上线)。此后 0.3.0、1.0.0
   照路线图。hotfix 走 PATCH(v0.2.1…),只修缺陷不排新功能。
2. **发车检查单**(标准化上线,顺序执行,任一步红=不发车):
   1. 产品层:npm test 全绿+架构门禁+真 PG 套件;迁移在生产影子库
      全链可迁(含 pg_trgm 前置确认);
   2. CLI 层:对产品层**真栈**冒烟(登录/列项目/提交一笔 dry-run 估价),
      合同漂移=红灯;
   3. Agent 层:wrapper 对产品工具调用合同的回归(鉴权/审计/费用确认
      红线用例);
   4. Eval 层:离线主链评测跑通+阻断条件零触发,出 audit receipt;
   5. 联调:四仓 RC 组合在 8080 影子栈全链走查(登录→生成→审核→交付);
   6. 上线:火山流水线 apply(VKE)→公网 smoke→UI 版本徽章更新;
   7. 收车:四仓打同名 tag+发版回执(docs/validation/release-vX.Y.Z.md,
      含各仓 commit 哈希对照表)。
3. **流水线现状与缺口**:火山持续交付现有 backend→dev、dashboard→main
   两条(服务 dev 团队线),**缺 integration/v011→VKE 的正式 apply 流水线**
   ——0.2.0 上线前置,建好后发车第 6 步才成立。
4. **分支纪律**:四仓统一以 integration/v011 为集成线(cli/eval 的该分支
   尚未 push,需 DC 授权推远端);发版从集成线切 RC,不从 main 发。
