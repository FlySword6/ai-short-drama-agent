# 设计:平均单集人时指标与趋势图口径(v0.2.x,DC 走查条 13)

状态:口径提案,待 DC 认可后进 k3 后端包 3 + Kimi 看板前端。
目标:数据看板出「平均单集人时」趋势图,对准 12 人时/集的经营目标
(盘点合成结论:现状≈15.7h,五杠杆到≈6h,outputs/logic-audit-synthesis-20260723.md)。

## 一、口径难点先说清

平台记录的是**事件**(生成请求、审核动作、保存、导入),没人填工时。
所以"人时"只能从事件流估,口径必须诚实标注是**平台内活跃人时**,
不是全口径工时。团队全流程在平台内做剧,这个近似是可用的;若将来
有大量平台外工作(如外部剪辑),口径要再议,不装全知。

## 二、计算口径(活跃段聚类法)

1. **归集维度**:episode(集)。每个事件带 user_id + episode_id + 时间戳。
2. **活跃段**:同一用户在同一集上的事件,相邻间隔 ≤30 分钟视为同一段;
   段时长 = 尾事件 − 首事件,再加 5 分钟收尾补偿(单事件孤段记 5 分钟)。
   30 分钟阈值与 5 分钟补偿进配置,不硬编码。
3. **集人时** = 该集所有用户所有活跃段时长求和。生成任务的机器等待
   不计入(等待期用户没有事件就自然断段,这正是我们要的:AI 跑批
   不算人力)。
4. **完成判定**:一集的人时终值在**交付门禁通过**时冻结(正好挂在
   产物审核+交付门禁包的状态机上,合同 output-review-and-delivery-gate.md);
   未交付的集在看板上单列"进行中",不进趋势均值。
5. **趋势图**:x=集的交付时间,y=该集人时;叠加近 5 集滚动均值线+
   12h 目标参考线。

## 三、数据源与缺口

| 事件类 | 现有真源 | 状态 |
| --- | --- | --- |
| 生成请求/确认/重试 | generation_requests(时间戳齐) | 可直接用 |
| 审核动作 | 审核域记录 | 可直接用 |
| 剧本/分镜编辑保存 | 部分接口有更新时间,**无逐次事件** | 缺 |
| 检索/资产引用 | 无事件表 | 缺 |

缺口用一张轻量 `activity_events` 表补(user_id/project_id/episode_id/
event_type/created_at,**不存正文**),服务端在写路径顺手记,前端不用改。
这张表与候选池里的「采纳行为埋点」(RaFe 飞轮,台账条 14/23)是同一张
表的两批 event_type——**合并成一个迁移做**,不建两套。

## 四、实施切分

- **k3 后端(包 3)**:activity_events 迁移+写路径埋点;聚合接口
  `GET /api/v1/dashboard/episode-person-hours`(按项目过滤,返回逐集
  人时+滚动均值,聚合逻辑在服务端,阈值可配);历史数据用
  generation_requests+审核记录回填近似值,标注 `backfilled: true`。
- **Kimi 前端**:看板加趋势图(ECharts,已有依赖),回填点用虚线/
  淡色区分,图例注明口径=平台内活跃人时。

## 五、诚实性约束

- 图上必须带口径说明入口(tooltip 或角标),写明"平台内活跃人时,
  30 分钟断段聚类";
- 回填的历史点与埋点后的真实点视觉区分;
- 不做"团队排名"类衍生视图——这是经营指标,不是员工监控,避免
  用错方向(本体论 R 系约束的精神:数据用途与采集口径一致)。
