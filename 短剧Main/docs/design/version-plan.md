## 为什么重排

原计划写死在前端一个静态数组里,没人记得改,于是:v0.1.2 / v0.1.3 至今挂着
"即将到来",而我们实际已在 v0.2.0;v0.2.0 上线了却根本没进预告;v0.2 那四张卡
(Pi 协作 / Cmd+K / 实拍混排 / 选题雷达)与实际交付的东西对不上;v0.3 十张卡
**完全没有后期流程**——时间线、剪辑、字幕、导出一个都没有,而那是短剧交付的
最后一公里。

## 编排原则

1. **档期按能走完的能力切,不按功能点凑数。** 一个档期结束时,用户应当能多完成
   一件完整的事,而不是多看到几个按钮。
2. **已发布的写实际交付物**,不写立项时的愿景。对不上就改计划,不改事实。
3. **治理字段固定,分类与标签可多值。** 每张卡固定有:档期、状态、负责方、
   起止时间、来源依据。主题标签允许并存,不强行唯一归类(依据 R9 与
   `creative-vocabulary-openness.md`)。
4. **缺口也要写进去。** 明知道缺的东西(比如后期流程)必须占一个档期位置,
   不能因为没想清楚就不写——不写等于假装不存在。

## 验收标准怎么写(S37 机制)

每张卡的验收标准(acceptance)是**内部判据,不上界面**——用户只看卡的 status。
它写在本文件里,是编辑源;`scripts/sync-release-plan.mts` 把它推进库,一致性
门禁逐字比对文档与库,**改一个字都会报红**。

写法:在所属档期段内、计划表**之外**放锚点块。锚点独占一行,靠 `card_key`
与卡关联(不靠标题);锚点后的非空行都是内容,到空行/表格行/标题行/下一个
锚点为止:

```markdown
<!-- acceptance:demo-example-card -->
交付物:示例——机制演示用假卡,不代表任何真卡
门禁:npm run check:architecture && npm test 绿
实打:在真环境跑过 `<命令>`,结果留痕在回执
```

规矩(DC 2026-07-26 口径):

- **三段式**:交付物 / 门禁 / 实打;进度靠逐条标 ✅/🔧,卡状态保持二元。
- **双阶段**:派包前 Fable 写判据意图进任务包,交付时执行者补具体命令。
- acceptance 可空:没写的卡不报错;但空锚点(下面没内容)是结构错误。
- 改验收只改本文件再跑同步;库里有、文档没有的验收,同步只报告不自动清,
  由人确认后处理。
- 内容本身(Fable 逐张查证据、真跑一遍)不由机制代写。

## 这份计划从哪推导(2026-07-28 立,必读)

**每一档都必须能从 `docs/design/product-goal.md` 推导出来;推导不出来的卡,要么总目标错了,要么那张卡是自嗨。**

- **两阶段目标**(DC 2026-07-28 拍板「两条都要,分阶段」):阶段一(→v1.0.0)= 专业剧组
  **12 人时做一集能上线的短剧**;阶段二(v0.4+)= 扩到个人创作者的创作平台。
  **底座按阶段二的标准打,界面按阶段一的需求做。**
- **走通优先于新功能**(DC 2026-07-28 复核仍作数):断头补完之前不开新功能面,上线流程除外。
  「走得通」=做了→看得到→回到该在的地方→知道下一步。
- **每个任务包必须回答一句**:它把「一集戏的一天」里哪一步的人时降下来了?回答不了就不派。
- **每档发版前跑一次全流程**(`docs/design/full-flow-screenplay.md`),任何断点 = P0,不清零不发版。
- **病根 1 仍是根**:以数据模型为中心组织界面而非以生产流为中心。修它的杠杆高于加任何新功能面。

## 排期怎么估的(2026-07-28 定,S82)

- **冲刺速度 ≠ 排期速度,这个区分是死的**:2026-07-26 13:02→07-28 12:34 的 47.5 小时里合流 41 个任务包(≈20 包/日),这是 AI 集群满负荷+决策人全天在线的**冲刺速度**;**排期一律按 ×0.5 = 10 包/日**,任何人不得拿冲刺速度当承诺。
- 折半三条理由:①21 个交付 tag 挤在 20.9 小时内(多执行通道同时满负荷),不可持续;②决策人零等待不可复现——标「待 DC」的闸历史平均等 4–12 小时;③剩余卡以后端结构类为主(3 包/卡,比前端清理类的 2 包/卡重),且真 PG 验收+迁移号串行分配天然限并行。
- 基准失效条件:执行通道数变化(订阅重置/429 停摆)、Fable 单点串行合流饱和、外部闸(算法备案 2–3 个月/测试站凭据/受控 env)不吃开发速度。

### Seedance 2.0 解锁前必须先解决的三件事(两份调研报告的结论,2026-07-27)

1. **提示词的「素材序号」引用是唯一的硬阻塞。** 2.0 要求提示词按「素材类型 + 序号」
   引用参考,序号是同类素材在请求里的顺序;而我们服务端用资产名、前端用另一套
   编号,两边都不满足。**这条不解决,多模态参考的准确率会一直偏低——而且我们
   现在就已经不合规了**,因为端点打的早就是 2.0。
2. **参数解冻被我们自己的价格下限卡住。** 报价代码里有一条按 fast 旧价定的
   80 分/秒硬下限;2.0 的实际单价未知,新档若低于它,报价会被自家代码拒掉。
   解冻画幅 / 时长 / 4K 之前先动这条。
3. **产物 URL 的 24 小时窗口是真实的数据丢失敞口,不是理论风险。** 过期字段恒空、
   转存失败无限重试且无上限无告警、worker 配置不全时静默不启动——三条叠起来,
   一次凭据配错就能让一批**已付费**的产物永久取不回,而系统全程不报警。

其余能力的落位(尽量不新开卡):延长视频并进「剪辑与转场」;4K 作为「成片导出」
的可选档;样片模式并进 v0.2.x 的「等待期的用户价值」二期;虚拟人像库与授权真人
素材并进「素材注册」;**联网搜索明确不做**——它只在纯文本输入下可用,与我们
「参考控制包为主路」的默认模式天然互斥。**一条待定**:编辑视频是新立「视频局部
编辑」还是并进「图片局部编辑」,等 Fable 定。

## 维护规矩

- 内容改动在**管理界面**里做,不改代码、不发版。
- 验收标准(acceptance)例外:它是内部判据,改本文件的锚点块、跑同步推进库——见「验收标准怎么写(S37 机制)」。
- 每个档期收尾时**核对一遍"计划 vs 实际"**,对不上就改计划,把实际交付写进已发布档。
- 新增卡片必须写清**起因**(哪个缺口、哪次事故、哪条吸收项),没有起因的卡片不进计划。
- **档期状态要与迁移台账和任务 DAG 对得上**(`docs/planning/orchestration.md`)——
  卡标零实现而迁移已经合流,门禁当场报红。合流之后先回写这两份真源,再跑门禁。
- **预告页只收「版本预告(对外)」那两张表里的条目**(R46):功能名 + 一句用户价值,
  bug fix、后端、清理类一概不上。改预告先改那两张表。
- **产品文档区(plane)是本文件的对外转写,不是第二个真源。** 档期或卡片有增删、状态有变化时
  同步更新那边,方向永远是本文件 → plane;不反向以 plane 为准。plane 那边只面向人类阅读,
  不放内部包号、执行人代号、迁移号与门禁数字。

**一个已知陷阱,写在这儿免得踩**:同步工具会把本文件新加的卡**照原文**推进库
(标题与内容一字不改地抄过去),而预告页目前**还没有"对内 / 对外"的分流**。
也就是说,在 S46 把分流做出来之前,新加的工程卡一旦同步进库就会直接出现在
用户看的预告页上——**这正是 R46 要治的病本身**。同步之前先想一眼:这张卡的
名字给不懂技术的业务看,合适吗?

### 口径修正:MAMMA 那条

1. MAMMA 是研究级多人无标记动捕,复刻它意味着数据集 + 训练 + 调优,是**数月的机器学习研究项目**,不是工程移植。

覆盖不了再议自研。**若 DC 坚持复刻,按坚持执行,但成本与周期需单独立项评估。**
