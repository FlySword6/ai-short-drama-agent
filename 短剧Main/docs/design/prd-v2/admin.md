# PRD v2·管理与运营章——v1 冻结稿 2026-08-02(裁决层;PRD 八章至此裁决层全冻结)

> 法源:R31 积分/R41·R41b 邀请码档位/V-37 10万seed/R114 冷启动入库/V-38 审核分层/R50④ 合规公示/R46 版本预告口径/R80 超管审核。
> 视觉真源=P-11(169:26)。实现现状:积分账本/邀请码送额度/RBAC 后端全通;P-11 前端=首批拆包;审核台在旧页(承接表 a 随块 1 迁)。

## 一、域定义

管理后台(P-11)=超管三件事:**审核**(通用资产+产物批次:传包→预检→确认→入库→发布/隔离,预检{通过N,待确认M}+文件级问题清单)、**账务**(积分总账/邀请码档位低代码可视化调整 R41b/管理员 10 万 seed 已实证)、**运营**(用户管理/模型档位与计价规则/雷达 admin 刷新位)。

## 二、硬边界

- 审核权:通用资产只有超管能审(V-38);个人域无审核概念(V-53);AI 候选层不自动转正(R116)。
- 计价规则改动=高影响(影响所有报价),改动走管理 API+审计留痕;档位数值统筹按官方成本自决(R154),界面上开放超管微调。
- 冷启动批量入库:仅超管+批次幂等+审计(R114);与资产登记队列(043)同一幂等体系。
- 合规公示位(R50④):关于页四件(备案号/公示链接/AI 标识说明/广电证号)——内部使用期不催办,上线前置(合规底稿三层在 outputs)。

## 三、验收判据

超管全流程:传包→预检→逐文件问题清单→确认入库→资产检索可见;邀请码建档→注册送对应额度→账本对平;计价规则改一档→新报价即用新价+审计有痕;非超管访问管理页=业务话拒绝。

## 四、后台五个模块的产生方式与操作边界(2026-08-06 落章)

> **来源**:丽芬 Figma 评论 `1872048877`(08-05 14:37 新增用户与编辑边界)、`1872052024`(14:39 积分与充值归属)、`1872054409`(14:40 邀请码)、`1872057264`(14:42 运营批次)、`1872060050`(14:44 平台配置)。
> 她问的是同一件事的五个面:**这些数据到底是后端自己长出来的,还是管理员在界面上建的?** 这一节把它答死。

### 4.1 五个模块逐个定性

| 模块 | 数据从哪来 | 管理员能做什么 | 要不要"新建"入口 |
|---|---|---|---|
| **用户管理** | 用户自注册产生 | 新增(手动开号)、调整积分、禁用、改角色 | **要**——补「新增用户」按钮 + 弹窗 |
| **积分与充值** | 账本按人累计,系统自动记 | 手动调额、看消耗明细 | **不要**新建入口。积分不是被"建"出来的 |
| **邀请码** | **管理员建**,不是后端自动生成 | 建码、设分档与赠送额度、设已用上限、停用 | **要**——「新建邀请码」按钮 + 弹窗 |
| **运营批次** | **后端自动产生**(超管冷启动批量入库时按批次落账,R114 幂等体系) | 只读查看、查问题文件、重跑 | **不要**新建入口;要有"查看详情" |
| **平台配置** | 一组固定的开关与数值,**随系统预置**,不是建出来的 | 改值(生成上限/新用户额度/未过审门禁/AIGC 标识/肖像相似度阈值) | **不要**新建入口;每项要有"改这项会影响什么"的一句话 |

**一条通用判据**:界面上出现"新建"按钮的前提是"这类东西确实由人创建"。后端自动产生的东西给"新建"按钮,是在骗用户。

### 4.2 积分与充值放在哪一页

- 积分粒度**按人配,不按项目配**(D-2 既有裁决,不变)。
- 丽芬据此问:既然按人,能不能和用户管理放同一页?
- **口径:不合并,但要互相跳得到。** 理由:用户管理一行是"这个人是谁、能干什么",积分是"这个人花了多少、还剩多少",两者读的人和读的频率不同;合并成一张表会把列撑爆。**做法**:用户管理行内的积分数值可点,点开直接跳到该用户在"积分与充值"里的明细;反向亦然。

### 4.3 用户可编辑的边界

丽芬原话:「每个用户是否可以编辑?但是需要敲定边界,什么时候可以编辑,可以编辑的内容有哪些?」

| 可改 | 不可改 | 说明 |
|---|---|---|
| 角色与权限、积分额度与日额度、启用/禁用状态、备注 | 登录账号(手机号/邮箱)、历史消耗记录、已产生的任务与资产归属 | 账号是身份锚点,改了会让审计断链;历史记录改了就不叫审计 |

- **禁用**是可逆的(停用/恢复),**不是删除**。用户删除本期不做——一删就会让他产生过的资产与任务失去归属。
- 所有编辑动作**入审计**:谁、什么时候、把什么从什么改成了什么。

### 4.4 【待拍板】一条

**新增用户走不走邀请码?** 两条路:①管理员直接开号(设初始密码/免密链接),与自注册并行;②管理员只发邀请码,人自己注册。选①要多做一套开号与初始凭据流程,选②则"新增用户"按钮其实是"生成一个邀请码"。**这条不定,新增用户弹窗画不出来。**

## 五、登录与会话(2026-08-11 产品负责人拍板)

本节是全平台会话规则的落章处。团队章 §3.3 的"改密后会话怎么办"指向这里。

### 5.1 同一个账号能不能在多处同时登录

**按环境分开定,不是一刀切。**

| 环境 | 默认 | 为什么 |
|---|---|---|
| 开发 | **能** | 几个人(和几个 agent)共用一个账号排同一个问题是常态。互相把对方踢下线,一轮排查就白费了 |
| 测试 | **能** | 同上。验收时产品负责人自己看片场,不该和执行方抢号 |
| 生产 | **只留一处** | 后登的把先登的挤下线。一个账号在多处活着,责任记录就说不清是谁干的 |

- 这三条**不需要运维显式配置**:不配任何东西,各环境就是上表的样子;
- 需要临时改的时候有一个显式开关能盖过默认——测试环境临时打开验证"挤下线"这件事本身,或者生产临时关掉排障;
- 撤销范围只覆盖**人工登录**(网页与命令行)。**Agent 凭据不在其内**:它是单独签发、单独吊销的东西,人重新登录一次不该把跑着的 agent 打断。

### 5.2 什么时候一定要把已有登录清干净

不管上面那个开关开着还是关着,下面三件事都必须让该账号**所有**在用的登录立刻失效:

| 动作 | 清理范围 |
|---|---|
| 管理员停用账号 | 该账号全部会话,含 Agent 凭据 |
| 管理员重置密码 | 同上 |
| **本人改自己的密码** | 同上(本次会话可以就地重签,不必让人自己也被踢出去) |

理由是一句话:**密码换了,拿旧密码换来的那些登录就不能再算数**——用户改密码往往正是因为怀疑密码泄露,这时候"别人那台设备上还登着"就是这件事最不能接受的结果。

> **实现现状(2026-08-11 核过)**:前两条已实现,在管理员停用/重置密码的同一事务里撤销。
> 第三条**尚无对应功能**——平台目前没有"本人改自己密码"的入口(团队章 §3.3 的首登改密还没建)。
> 建这个入口的人必须在同一事务里做撤销,**不能指望"下次登录时顺手撤销"**:那个撤销现在按环境开关走,开发和测试根本不会执行。

### 5.3 验收判据

- 开发环境:同一账号在两处先后登录,先登的那处继续能用;
- 测试环境:同上;
- 生产环境:同一账号在两处先后登录,先登的那处失效,提示重新登录;
- 显式开关能双向盖过上面的默认;
- 管理员停用/重置密码后,该账号所有登录立刻失效(含 Agent 凭据);
- 上述任何一条改动,都不得动到"改密或停用与新建会话之间的竞态防护"——那是另一件事,拆开审。

### 5.4 用户看到什么

被挤下线的那一处,下次操作时看到的是"登录已失效,请重新登录",不出现英文、状态码或内部状态名。文案键归文案章管辖。
