## 一、域定义与边界

### 1.1 管什么 / 不管什么

| 管 | 不管 |
|---|---|
| 团队的创建、名称、成员名单、归档 | 项目里谁能干什么(项目章 §三) |
| 团队内角色(团队管理员 / 普通成员)这个身份,以及它能对成员做什么 | 平台角色枚举本身(`admin`/`operator`/`member`,后台章) |
| 直接开号加人的完整流程,含初始密码与首登改密 | 自助注册流程的字段与验证(后台章) |
| **团队维度的成本可见范围**——这是本章新开的一项数据可见性授权,不是「引用已有能力」 | 积分怎么扣、价格怎么算(账务) |
| 团队被归档后的产品后果 | 团队作为成本归集父子层级的既有用法(见 §1.4) |

**一条判据**:凡是「这个人属于谁的班子、怎么进来的」归本章;凡是「这个人在某个项目里能干什么」归项目章——**团队第一步不改变任何项目权限**。

**一处必须说清的例外(审计分歧 1)**:让团队管理员看到自己团队的成本汇总,**本身就是一次数据可见性授权的扩大**,不能用「已有能力,本章只引用」带过。今天的成本接口只认平台管理员或运营账号(`assertOperatorOrAdmin`,`src/modules/operations/repository.ts:1087`),团队管理员一条都看不到。本章新增的范围写死在 §3.7。

### 1.2 团队不是项目权限模型——这句话的准确版本

现有代码注释写的是「Teams are cost-attribution units. They are not an additional permission model」(`src/db/schema.ts:175-177`)。本章生效后这句话要同步改成准确版本:

> **团队不构成项目访问权限模型;项目成员关系仍然是项目访问的唯一依据。团队承载的是成员管理与团队成本读取这类「资源范围内的管理授权」。**

不改这句注释,后端会有两种走偏:要么继续沿用「只有平台管理员能操作」的旧接口,要么放宽接口时漏掉「目标团队范围」的校验。

### 1.3 8-17 试点交付范围(显式写死,不让人从依赖图里猜)

**8-17 交这些(映射 #181「团队功能第一步:总导演能自己开号拉班子」):**

1. 平台管理员建团队并指定团队管理员;
2. 团队管理员直接开号,新号自动进本团队;
3. 新号首次登录强制改密;
4. 团队管理员与普通成员都能看到本团队名单;
5. 团队管理员移出成员(带界面明示);
6. 团队管理员看本团队成本总额与按成员汇总;
7. 团队管理员能建项目,并把成员加进项目(建项目与加项目成员的规格归项目章,本章只负责能力可用与衔接指引)。

**8-17 不交这些(不在范围内,验收不得据此问责):**

- **邀请码整条后置**——邀请加入、邀请码生命周期、邀请码状态机全部不做。理由:试点人员没有已有平台账号(产品负责人 2026-08-10 事实答复),直接开号已经覆盖全部试点场景,没必要为此背上 #72 邮件通道这条依赖;
- 把**已有平台账号**拉进团队(见 §1.4);
- 团队层级在界面上的任何暴露;
- 团队级积分池;
- 跨团队转移。

### 1.4 明确不做的,以及对既有能力的对账

| 不做 | 配套说明 |
|---|---|
| **不做**「团队成员自动看到团队项目」 | 项目可见性仍以项目成员关系为唯一依据。团队作为权限边界是另一个方向,验证过第一步的真实用法后单独立项 |
| **不做**团队层级(团队下再分组) | **对账**:`teams.parent_team_id` 一层父子**今天已经存在**(`src/db/schema.ts:183`,DB 触发器 `teams_assert_one_level` 约束只能一层,`migrations/016_operations_foundation.sql:75`),它是给成本归集用的,代码注释写明「never an auth edge」。**它和本章禁止的权限层级不是一回事,不构成冲突;本章不把它暴露给团队管理员,界面不显示、不可编辑** |
| **不做**成员跨团队转移 | **对账**:今天没有「把已有平台账号拉进团队」的路子——两条加人路一条是建新账号、一条是自助注册成新账号。**这条声明为边界,排在试点之后**。依据:试点人员无已有账号(2026-08-10 事实答复)。试点期若真出现已有账号要进团队,替代路径=平台管理员走既有 `POST /api/v1/admin/teams/:team_id/members` 直接加,不走团队管理员通道 |
| **不做**团队级积分池 | 新成员的额度仍按人配(后台章 §4.2),团队管理员没有充值权;试点期额度由平台管理员统一配 |
| **不做**硬删团队 | **对账**:`DELETE /api/v1/admin/teams/:team_id` **今天已经存在**(`src/modules/operations/routes.ts:215`),而且会顺着数据库外键把 `team_members` 全部记录一起抹掉(`src/db/schema.ts:189`,`onDelete: "cascade"`)。改法见 §3.8:语义改软删/归档,试点前把入口从管理界面收起 |

## 二、用户故事

> 角色词按 §6.1 消歧表:**总导演**=业务称谓(人),**团队管理员**=`team_role='admin'` 的管理授权,**生产身份**=D14 项目内概念(编导/抽卡师/音频/剪辑),**平台管理员**=平台角色 `admin`。四者不互换。

### US-1(主线)总导演开号拉班子:开号 → 建项目 → 加进项目 → 成员登录即可编辑

- **GIVEN** 平台管理员已经建好团队「合肥动漫一组」,并把总导演小陈指定为该团队的团队管理员;小陈已登录;
- **WHEN** 小陈在「我的团队」里给抽卡师小李开一个号(填用户名与显示名),把界面上一次性展示的初始密码私下交给小李;**AND** 小陈新建项目《老公诈死》;**AND** 小陈在项目设置里把小李加为该项目的编辑者;**AND** 小李用用户名和初始密码登录,按提示改掉密码;
- **THEN** 小李进入平台后,在项目列表里能看到《老公诈死》,并且能在里面建集、传资产、发起生成;**AND** 小陈这一串动作在审计里各留一条记录,记录里没有任何明文密码。

**这条故事是本章的成败判据。** 中间任何一步断了,「拉人开工」就没做到。其中「新建项目」与「加项目成员」的规格归项目章 §2 与 §3.2,本章只保证团队管理员**有**这个能力(§3.9)并给出衔接指引。

### US-2(边界)开号撞名

- **GIVEN** 平台上已经有一个用户名叫 `xiaoli` 的账号;
- **WHEN** 团队管理员用 `xiaoli` 这个用户名开号;
- **THEN** 开号不成立,界面提示「开号没成:这个用户名已经有人用了,换一个再试。」;**AND** 数据库里不产生半个账号、也不产生团队成员记录(事务整体回滚);**AND** 不产生也不展示任何初始密码;**AND** 不产生 `user_created` 审计记录。

### US-3(边界)团队被归档

- **GIVEN** 团队「合肥动漫一组」有 4 名成员,其中 3 人分布在 2 个项目里,团队名下已经产生过成本记录;
- **WHEN** 平台管理员把这个团队归档;
- **THEN** 这个团队不再出现在团队列表和成员的「我的团队」里;**AND** 4 个账号照常能登录;**AND** 3 人在 2 个项目里的成员记录、项目角色、访问能力**逐条不变**;**AND** 已经产生的历史成本记录不丢失、仍可按团队查询到;**AND** 归档动作入审计。

### US-4(边界)普通成员看自己的团队

- **GIVEN** 抽卡师小李是团队「合肥动漫一组」的普通成员;
- **WHEN** 小李进入「我的团队」;
- **THEN** 他能看到团队名称和完整成员名单(显示名、团队内角色);**AND** 界面上没有加人、移出、看成本的任何入口;**AND** 他直接调用加人或移出接口会被拒。

### US-5(边界)移出成员之后

- **GIVEN** 抽卡师小李是团队成员,同时是项目《老公诈死》的编辑者;
- **WHEN** 团队管理员把小李移出团队,并在确认框里读到「他现在能进的项目,移出后还是能进」;
- **THEN** 小李不再出现在团队名单里;**AND** 小李的账号照常能登录;**AND** 小李在《老公诈死》里仍然是编辑者,仍能打开、下载、编辑;**AND** 小李已经产生的历史成本仍计入该团队的成本汇总,在按成员汇总里以「已移出」标注呈现。

### US-6(边界)团队管理员离岗,团队没有在岗管理员

- **GIVEN** 团队管理员小陈的账号被平台管理员停用;
- **WHEN** 团队其他成员照常工作;
- **THEN** 成员登录、进项目、生成一切照常;**AND** 团队名单仍然可见,并显示「这个团队现在没有在岗管理员」;**AND** 加人与移出这两件事没人能做,直到平台管理员另行指派新的团队管理员;**AND** 指派完成后,新管理员立即可用全部管理动作,小陈(即便被恢复)不再有。

## 三、功能规格(字段级)

### 3.1 团队内角色:团队管理员建在哪

**结论(2026-08-10 拍板,不重开)**:团队管理员 = **团队成员表新增一列「团队内角色」**,**不动平台角色枚举**。

| 项 | 规格 |
|---|---|
| 放在哪 | `team_members` 新增列 `team_role` |
| 类型 | `varchar(16)`,`not null`,`default 'member'` |
| 枚举 | `admin` \| `member`(全列,无第三值) |
| 唯一性 | 同一个团队**有且只有一名** `team_role='admin'`——用 `team_id` 上的部分唯一索引(`where team_role = 'admin'`)在数据库层保证,不靠应用层自觉 |
| 兼任 | **一个人可以同时是多个团队的团队管理员**。`team_members` 主键是 `(team_id, user_id)`,天然支持;不加额外限制 |
| 平台角色 | **一个字都不改**。`PLATFORM_ROLES = ["admin","operator","member"]`(`src/modules/operations/types.ts:8`、`src/db/schema.ts:27`)保持三值 |

**归轴表述(写进词表,§6.1)**:团队管理员**不是**四条正交轴的第五轴,**也不是**任何一条轴上的新枚举值。它是**资源范围内的管理授权**——与访问权限轴平行,但作用域限定在**单个团队**。这与项目章「所有者」的既有模式同构:所有者不是平台角色的第四值,而是 `project_members.role` 里的一个取值。

**鉴权谓词**:新增 `assertTeamAdmin(db, userId, teamId)`,判定条件三条同时成立——① `team_members` 里存在 `(teamId, userId)` 行;② 该行 `team_role = 'admin'`;③ `users.active = true`。现有 `assertAdmin`(`src/modules/operations/repository.ts:1081`,原文「只有管理员可以管理团队和用户分组」)与它的 14 处调用点**保持不动**,平台管理员的既有能力一条不减。

### 3.2 直接开号(8-17 唯一的加人路)

团队管理员在「我的团队」里填新成员的用户名和显示名,系统建号、把号加进本团队、一次性展示初始密码。

**输入字段:**

| 字段 | 必填 | 类型与校验 | 默认 | 说明 |
|---|---|---|---|---|
| 用户名 | 是 | 3–64 位,小写字母/数字/点/横线/下划线,首位必须是小写字母或数字(沿用既有规则 `^[a-z0-9][a-z0-9_.-]{2,63}$`,`src/modules/admin/users/service.ts:15`) | 无 | 全平台唯一 |
| 显示名 | 否 | ≤128 字 | 缺省取用户名 | |
| 平台角色 | —— | **不接受入参** | 强制 `member` | **团队管理员开不出管理员号或运营号,这是边界**;接口收到 `role` 字段一律拒绝请求,不做静默忽略 |
| 团队内角色 | —— | **不接受入参** | 强制 `member` | 团队管理员开不出第二个团队管理员 |
| 界面模式 | 否 | `lite` \| `full` | `full` | 沿用后台既有默认 |

**行为(单事务,全成或全不成):** 建账号 → 置「必须改密」标记 → 写 `team_members` 行(`team_role='member'`)→ 写两条审计 → 返回初始密码。任一步失败整体回滚。

**输出:** 新账号信息 + **初始密码明文,仅此一次**。初始密码不进任何列表查询、不进审计记录、不进服务端日志、不进响应缓存。

**初始密码规格(2026-08-10 拍板):**

| 项 | 规格 |
|---|---|
| 长度 | **不少于 12 位**(拍板值 12 位是下限;现有实现已经是 20 位起,不得因为本条改弱——见拟稿说明「拿不准 1」) |
| 字符集 | 大写字母 + 小写字母 + 数字 |
| 随机性 | 密码学安全随机源 |
| 返回次数 | **只在创建响应里返回一次**;之后任何接口、任何角色都读不回来 |
| 失效 | **不设失效。这是明示取舍,不是遗漏**——产品负责人 2026-08-10 明确否掉了「初始密码限时失效」这一条。安全底线由「首登强制改密」承担(§3.3) |
| 重新生成 | 团队管理员**没有**重发密码的入口。成员忘记密码走平台管理员既有的重置通道(`POST /api/v1/admin/users/:id/reset-password`) |
| 落盘 | 只存哈希,不存明文;审计记录与日志一律不含明文密码 |

**异常路径(每条给业务话文案,键见 §七):** 用户名撞名 → 开号不成立、整体回滚;用户名格式不对 → 提示格式要求;团队已归档 → 不能开号;调用者不是本团队的团队管理员 → 拒。

**审计:** `admin_user_actions.user_created`(账号本身)+ `admin_operation_actions.team_member_added`(团队归属),同一事务写入,两条都不含明文密码。

### 3.3 首登强制改密

「提示改密」这个非强制说法作废,改成可测谓词:

> **新开的账号首次登录后处于「待改密」状态。在改密完成之前,除改密相关的三个端点之外,该账号的一切请求返回 403,响应是业务话。**

| 项 | 规格 |
|---|---|
| 放在哪 | `users` 新增列 `must_change_password`,`boolean`,`not null`,`default false` |
| 置真 | 团队管理员开号时置 `true`;平台管理员重置密码时同样置 `true` |
| 置假 | 改密成功的同一事务里置 `false` |
| 放行清单(全列) | ① `POST /api/v1/auth/password/first-change`(改密本身)② `GET /api/v1/auth/me` 或同等的当前用户/能力查询(前端据此判断跳转)③ 退出登录 |
| 其他一切请求 | 403,业务话文案见 §七 `auth.password.first_change.blocked`;**不得实现成可以点掉的置顶提示或可跳过的弹窗** |
| 新密码校验 | 沿用平台既有密码规则(后台章),不在本章另造一套 |
| 改密后 | **本人改完密码,他自己其余设备上的登录一律失效**,必须重新登录。见后台章 §五「登录与会话」。这一条不受「同一账号能不能多处登录」那个开关影响——改密撤销是安全动作,多处登录是便利设定,两回事 |

**为什么必须强制**:初始密码是团队管理员亲手交出去的,他本人长期知道这个密码。团队管理员和成员关系破裂(试用期没过、临时工被辞退)是内容行业常态。不强制改,这就是一个随时可以冒用的后门。

### 3.4 看团队名单

**普通成员能看到自己团队的名单**(2026-08-10 拍板,解掉审计分歧 3 的文字矛盾)。

| 谁 | 看得到什么 | 能做什么 |
|---|---|---|
| 团队管理员 | 团队名 + 完整名单(显示名、团队内角色、加入时间) | 加人、移出、看成本 |
| 同团队普通成员 | 团队名 + 完整名单(同上字段) | **只读**。界面上不出现加人/移出/成本任何入口 |
| 不是这个团队的人(含其他团队的管理员、未加团队的普通成员、运营账号) | 什么都看不到,**连团队存不存在都不告诉他** | 无 |
| 平台管理员 | 全部团队(走既有管理通道) | 全部;**看他人团队名单留痕**(比照项目章 §3.3「看到即留痕」) |

**名单里不出现的字段**:成员的密码相关任何信息、成员在其他团队的归属、成员的个人成本数字(成本只在 §3.7 的成本视图里出现)。

### 3.5 移出成员

**移出 = 离开团队。账号不删、不停用、不碰他名下任何项目。**

这条是**刻意设计,而且和直觉相反**,所以必须在界面上讲透:

- 确认框里明示:**「他现在能进的项目,移出后还是能进——要收回,去对应项目的设置里把他移出项目。」**(文案键 `team.member.remove.confirm.body`);
- 完成提示里再说一次「他的项目访问没有变化」;
- 验收补正向断言:移出前后,该成员在所有项目里的成员记录、项目角色、生产身份、实际访问能力**逐条不变**(§八 D 组)。

**不能被移出的人**:`team_role='admin'` 的团队管理员本人。团队管理员**不能自我卸任**(2026-08-10 拍板),接口对「移出对象是本团队管理员」一律拒绝并给业务话,要换人只能由平台管理员走 §3.6。

**移出后的成本归属**:该成员已经产生的历史成本**仍然计入本团队**,在按成员汇总里以「已移出」标注呈现(§3.7)。

**审计**:`admin_operation_actions.team_member_removed`。

### 3.6 团队管理员的生命周期(2026-08-10 拍板,五条写死)

| 场景 | 规格 |
|---|---|
| **不能自我卸任** | 团队管理员没有任何路径把自己降为普通成员或移出团队。换人只有平台管理员一条路 |
| **可兼任多团队** | 一个人可以同时是任意多个团队的团队管理员。各团队的管理动作彼此独立,看不到别的团队 |
| **更换** | 只有平台管理员能换。动作是原子的:新人置 `team_role='admin'`;**旧管理员降为 `team_role='member'`,仍留在团队名单里**(比照项目章「所有者转让后自己降为编辑者」)。新人必须已经是本团队成员,不是则先加进来 |
| **旧管理员的权限何时收回** | **立即**。更换事务提交后的下一个请求起,旧管理员的加人、移出、看成本全部被拒;**成本查看权即时失去**(2026-08-10 拍板) |
| **被禁用 / 离职** | 平台管理员**另行指派**。空窗期内团队处于「无在岗管理员」状态:成员登录、进项目、生成一切照常,只是**没人能加人和移人**,界面上明示这一点(文案键 `team.no_admin.notice`)。系统不自动挑人接任 |

**审计**:`admin_operation_actions.team_admin_assigned`(建团队时首次指定)、`team_admin_replaced`(更换,元数据含旧新两人)。

### 3.7 团队成本可见范围(2026-08-10 拍板)

团队管理员能看**自己团队**的:

| 给看 | 不给看 |
|---|---|
| 团队**总消耗** | 单笔消耗 |
| **按成员汇总**(每人一行合计) | 项目名 |
| 时间范围筛选(起止日期,沿用既有成本接口的筛选口径) | 模型名 |
| 已移出成员的历史合计(标注「已移出」) | 供应商名 |

**三条附加口径:**

- **移出成员的历史成本仍计入本团队**,不因为人走了就从团队总额里扣掉——账要对得上;
- **管理员更换后,旧管理员立即失去成本查看**;
- 团队管理员只能看自己团队,别的团队的成本一个数字都看不到;跨团队的成本查询仍然只归平台管理员与运营账号(既有 `GET /api/v1/admin/costs`)。

界面上要有一句说明:「这里只看得到团队总消耗和每个人的合计,看不到具体花在哪个项目、哪一单。」——把边界写在选项里,不静默失效(文案章三法则之三)。

### 3.8 团队删除:改软删 / 归档语义

**现状对账**:`DELETE /api/v1/admin/teams/:team_id`(`src/modules/operations/routes.ts:215`)今天是硬删,而且顺着外键把 `team_members` 全部记录一起抹掉(`src/db/schema.ts:189`)。平台管理员今天就能把整个试点团队连带成员归属一次性删掉,删完没有任何产品定义兜底。

**改法:**

| 项 | 规格 |
|---|---|
| 数据 | `teams` 新增 `deleted_at`(`timestamptz`,可空)。仓里多张表已经是这个模式(如 `projects`),不新造 |
| 语义 | 归档,不是删除。写 `deleted_at`,**不删任何行** |
| 产品后果(写死) | **归档团队不清成员的历史项目记录**:成员账号、项目成员记录、项目角色、生产身份、已产生的资产与任务归属、历史成本记录——**一样都不动** |
| 归档后 | 团队不出现在团队列表与成员的「我的团队」里;不能再往里开号或加人;历史成本仍可按团队查到 |
| 恢复 | 平台管理员可以把 `deleted_at` 置空恢复。试点期界面不给这两个入口 |
| 试点前的动作 | **把硬删入口从管理界面收起**——界面上不出现「删除团队」按钮 |
| 审计 | `admin_operation_actions.team_archived` / `team_restored` |

### 3.9 团队管理员建项目的能力从哪来(接住审计共识 2)

**拍板**:试点项目由总导演自建,开号→建项目→拉人一条龙。

**做法(本稿的细化选择,见拟稿说明「拿不准 2」)**:给**团队管理员豁免**——`team_role='admin'` 的用户在能力查询里天然带 `project:create`,不受部署级开关约束。

**为什么不直接放开开关**:`ALLOW_MEMBER_CREATE_PROJECT` 是进程级环境变量(`src/config/env.ts:103`、`src/config/env.ts:344`),`platformPermissions`(`src/modules/operations/repository.ts:1268-1272`)里普通成员拿不拿得到 `project:create` 完全由它决定。**放开它,试点环境里所有普通成员都能建项目**,不只是团队管理员——影响面比拍板本意大。

**退路**:如果豁免这条改动来不及,退回「试点环境放开 `ALLOW_MEMBER_CREATE_PROJECT`」,但必须在试点前确认这个开关在试点环境的实际取值,并接受「所有成员都能建项目」这个后果。**不管走哪条,这个开关的取值必须在试点前被确认下来,不能继续隐身**(§九列为前置)。

### 3.10 衔接指引:开完号,总导演紧接着要做什么

**这一段是本章的防断点。** 开号成功后,新成员**不在任何项目里**,登录进去项目列表是空的——这是「项目可见性以项目成员关系为唯一依据」这条既有原则的必然结果,不是缺陷。

界面在开号成功页要直接给出下一步:

> **号开好了,他还进不了任何项目。下一步:建项目(或打开已有项目)→ 到项目设置里把他加进去并给角色。**

- **建项目**:归项目章 §二。团队管理员的建项目能力见 §3.9;
- **加项目成员、给项目角色(所有者/编辑者/查看者)**:归项目章 §3.2——从平台已有用户里选,选完指定角色;
- **生产身份(编导/抽卡师/音频/剪辑,`prd-spine.md` §三之 2 定的真实四岗)**:项目内概念,归项目章,与团队内角色无关。

### 3.11 邀请加入(整条后置,不在 8-17 范围)

团队管理员生成一个绑定自己团队的邀请码,对方走自助注册,注册成功自动进团队。

**本版不写字段规格、不写状态机、不写接口——整条后置。** 理由与依赖:

- 试点人员没有已有平台账号,直接开号已覆盖全部试点场景;
- 自助注册的邮箱验证码依赖真实邮件通道(#72「接通注册验证码的真实邮件发送通道」),该卡未完成;
- 团队邀请注册还要求注册接口接受邀请码参数,**这是对后台章注册流程的跨章改动**,届时要在后台章一并认领,不能两边都不管;
- 与现有的「注册送积分邀请码」是两回事,届时不许混用一张码。

**解冻条件**:#72 接通 + 产品负责人重新把它排进某个版本。届时本节按九节标准补齐字段规格、状态机(§5.4 已留位)与接口。

### 4.2 改造既有端点

| 端点 | Method | 改什么 | 审计动作 |
|---|---|---|---|
| `/api/v1/admin/teams` | POST | 请求体新增 `admin_user_id`(必填):建团队的同时指定团队管理员,同一事务写 `team_members` 行并置 `team_role='admin'` | `team_created` + `team_admin_assigned` |
| `/api/v1/admin/teams/:team_id` | DELETE | 行为从硬删改软删:写 `teams.deleted_at`,不删任何行(§3.8) | `team_archived` |

| `/api/v1/users/me/capabilities`(既有能力查询) | GET | 响应新增当前用户在各团队的 `team_role`;`project:create` 的判定纳入团队管理员豁免(§3.9) | 无(读) |

### 4.3 三条全局约定

1. **不泄露存在性**:调用者不是目标团队成员时一律 **404**,不是 403——比照运营底座既有先例「非成员 404 不 403,不泄露项目存在性」。已经是成员但权限不够(普通成员做管理动作)才用 **403**,因为存在性他本来就知道。
2. **错误响应体**:走全站统一信封,`message` 是中文业务话(文案章三法则),`code` 只给程序判断、永不上屏;**响应体任何情况下不得包含**目标团队名称、人数、成本数字、成员用户名。
3. **初始密码只出现在一个地方**:开号接口的 201 响应体。不进日志、不进审计元数据、不进任何其他接口的响应。

## 六、数据与词表

### 6.1 词表新增与消歧

**新入词表的词条(四条):**

| 词 | 一句话定义 | 边界 |
|---|---|---|
| **团队** | 一个班子的成员名单 + 一个成本归集口径 | 不是项目访问权限的依据 |
| **团队管理员** | 团队内角色为 `admin` 的成员;在本团队范围内能加人、移出、看团队成本汇总 | 不是平台角色,不是项目角色,不是生产身份;作用域限单个团队 |
| **团队内角色** | 成员在某个团队里的身份,取值 `admin` \| `member` | 与平台角色、项目角色、生产身份四者独立,不合并成一个枚举 |
| **首登改密** | 新开账号首次登录后必须先改密码,改完之前进不了业务功能 | 不是提示,是拦截 |

**消歧表(四个容易被合并的称谓,一个都不许互换):**

| 称谓 | 是什么 | 存在哪 | 作用域 |
|---|---|---|---|
| **总导演** | 业务称谓,指带班子的那个人 | 不落库,只在叙述里用 | —— |
| **团队管理员** | 资源范围内的管理授权 | `team_members.team_role = 'admin'` | 单个团队 |
| **生产身份** | D14 项目内概念,取值是 `prd-spine.md` §三之 2 的真实四岗:**编导 / 抽卡师(即提示词工程师) / 音频 / 剪辑**,四者非互斥、可兼任 | 项目成员的生产身份 | 单个项目 |
| **平台管理员** | 平台访问级 | `users.role = 'admin'` | 全站 |

**为什么必须消歧**:D14 定的四条正交轴明文「四者不得合并成一个角色枚举」。「团队管理员——就是这个班子的总导演」这种写法会把业务称谓、管理授权、生产身份三样东西混成一个,后端顺手往平台角色枚举加第四值就是直接违规。
