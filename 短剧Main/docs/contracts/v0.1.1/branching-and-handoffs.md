# 分支、并行开发与交接合同

## 基线

本仓所有新工作包以最新 `origin/dev` 为基线，唯一集成目标也是 `dev`。`integration/v011`、`origin/main` 和旧仓只提供历史取证或可选择迁移的能力，不作为新分支或合并基线；禁止把这些分支直接 merge 进 `dev`。

## 分工矩阵

| 角色 | 范围 | 交付物 |
|---|---|---|---|
| Coordinator | 核实真源、拆工作包、分配文件与共享资源、维护 Project/Issue/版本账实 | 工作包边界、依赖、验收与状态对账 |
| Implementer | 在独立 worktree 修改获分配的目录，补测试并给出不可变提交 | feature 分支、commit SHA、检查与交接 |
| Independent Verifier | 在独立只读环境按原始合同复验不可变提交 | 独立结论、finding 与复现证据 |
| Merge Authority | 核对 PR 指向 `dev`、正式工作项、独立复核与 PR 闸 | 合并授权和远端读回 |

边界与例外：

- 每个工作包在开工时按当前人员与会话映射角色，不把历史执行者固化为永久所有者。
- 根 `package.json`/lockfile、migration ledger、schema、KMS helper 和部署清单都是共享单写者资源，修改前必须显式分配。
- 交付方式默认是本地 feature 分支 + 不可变提交 + 回执；只有当前任务明确授权时才 push 并创建指向 `dev` 的 PR。
- push、合并、部署、生产变更、密钥操作、付费调用和其他远程写入分别需要当前动作的明确授权，不得互相推导。

## 并行规则

- 每个工作包一个分支/worktree，一个明确负责人和目录范围。
- 同一文件同一时间只有一个写者；需要共同修改时由集成人统一收口。
- 前端、后端、数据库、Docker 可在目录不重叠时并行。
- 先合底层合同和适配器，再合业务服务，最后合页面；数据库迁移先于依赖它的代码。
- 所有代码改动只通过 PR 进入 `dev`；`test` 是部署面，只接受 `dev` 单向推进，不直接接收功能 PR。

## 迁移号分配与数据库护栏（2026-07-26，S22 立项）

多包并行下迁移号不靠人记。纪律如下，机器部分已进 `npm test` 门禁：

- **迁移号区间由 Fable 在新包立项时分配**，写进任务包；包内不得自行占号、不得跨区间用号。当前分配：001–020 已入集成线；021 = S20；022 = S22（未使用即退回池）。
- **编号连续唯一**:`scripts/check-migrations.mts` 校验 001…N 不跳号、不重号，迁移器无法识别的文件名（会被静默跳过）同样报错。
- **checksum 台账**：新迁移提交前必须 `npx tsx scripts/check-migrations.mts --update-ledger` 入账 `migrations/ledger.json`；台账只增不改，已入账迁移禁止事后修改——结构变更一律新增迁移（迁移器在已应用库上会对 checksum 不一致报错，台账把发现提前到提交前）。
- **扩展集中声明**：迁移依赖数据库扩展（如 017 依赖 `pg_trgm`）必须在 `migrations/extensions.json` 登记并注明依赖它的迁移；迁移体内禁止 `CREATE EXTENSION`（扩展是 DBA 预置条件）。部署与本地环境按该文件预装；`--list-extensions` 可回答"这套迁移需要哪些扩展"。
- **结构双真源**:`src/db/schema.ts` 与迁移重放结果的漂移由 `scripts/check-schema-drift.mts` 检测（本地临时 PG，可用 `-docker.sh` 一键）；迁移创建但刻意不进 Drizzle 的对象必须带理由登记在脚本白名单内。
- **演示数据集**:`seed/`（幂等、无真实凭据）由 S22 产出、S21 一键起环境时调用。

## 迁移要求

迁移外仓代码时先列出：来源提交、要保留的能力、不要带入的框架/依赖、目标目录、数据映射和验证方式。禁止整仓复制、直接 merge 或保留第二套登录/数据库/模型调用。

## 交接格式

每个工作包必须提供：

1. 分支和提交；
2. 修改文件及用户可见变化；
3. 数据/API/环境变量变化；
4. 已运行检查和结果；
5. 尚未验证与已知限制；
6. 人工复验步骤；
7. 是否涉及付费、远程写入或部署。

集成人重新运行完整检查，不以子代理"已通过"代替最终验证。
