# PostgreSQL 14 与 16 定策（一页纸）

> 状态：`DECIDED_FOR_V0.3.0`
> 日期：2026-07-22
> Owner：DC
> 范围：短剧生产主库；不改变既有 RDS、账号、数据或部署。

## 结论

**V0.3.0 至首次生产上线，锁定 PostgreSQL 14 兼容，生产继续使用已验证的 PG14.17。现在不为“版本更新”升级到 PG16。**

这里的“锁定”是最低兼容基线和生产运行版本，不是永久禁止 PG16。代码、迁移和测试不得依赖
PG15/16 专有行为；当下面的升级触发条件出现时，再走一次受控的 PG16 升级窗口。

## 已观察到的事实

| 事实 | 证据 | 对决策的意义 |
| --- | --- | --- |
| 云端目标 RDS 是 PG14.17，生产账号与空 `prod` schema 已建立 | `v0.1.1-production-database-governance-receipt.md` 第 1 节 | 当前真实环境不是假设，继续 PG14 没有版本迁移风险 |
| 001–012 已通过生产 `verify-full` TLS 执行，账本 12 行、表 31 张，幂等复跑为 up to date | 同上 | 已有生产结构证据，不能为了升级版本重开基础迁移风险 |

| 当前数据库设计使用标准 SQL、事务、外键、部分索引、JSONB 和 advisory lock，没有已批准的 PG16 专有依赖 | 001–013 migration 与现有 repository 合同 | 目前没有“必须升级”的产品或技术收益 |

## 为什么不现在升级

PG16 的潜在收益（性能改进、维护生命周期更长）是真实的，但在当前阶段不能抵消以下确定成本：

1. 生产 RDS 大版本升级是有状态变更，回退通常靠快照恢复，不是一次普通代码回滚。
2. 现有 PG14 已完成账号、schema、TLS、migration 账本和最小权限验证；PG16 尚无同等真环境证据。
3. 当前主矛盾是把控制包、生成链路和前端接入完成，不是数据库引擎性能。提前升级会把上线风险从业务实现转移到基础设施。

因此本阶段采取“**先用已验证的 PG14 上线，持续保持 PG16 可迁移性**”的路线。

## PG16 的准入触发条件

满足下列任一业务或运维理由，才立项升级；“想用最新版”不是触发条件：

- 火山 RDS 对 PG14 的支持、补丁或合规要求发生变化，需要迁到受支持主版本；
- 已复现且量化的 PG14 性能、并发或运维瓶颈，且通过索引、查询、连接池和资源调整无法解决；
- 已批准的产品能力确实需要 PG15/16 专有特性，并在架构合同中写明不能用 PG14 等价方案；
- 新建生产环境必须使用 PG16，且不存在需要继续承载的 PG14 数据。

## 升级前硬闸门

任何触发后，仍必须全部通过下列门禁才能改生产 RDS：

1. 建立与生产同版本数据结构相同的 PG16 隔离环境；禁止直接拿生产首试。
2. 从冻结的生产快照或经批准的去敏副本恢复演练，验证 schema、账号、`search_path`、TLS `verify-full`、TOS/Milvus 派生链不变。
3. 在 PG16 执行 001–013 全迁移及幂等复跑；正式迁移账本 checksum 与文件一致。
4. 跑全量测试、关键 repository 真库测试、登录/资产检索/控制包/报价确认的无付费冒烟；不得只测建表成功。
5. 完成性能基线对比：至少覆盖资产检索、生成任务创建、审核并发和控制包读写；结果要说明升级获得了什么。
6. 控制台确认备份可恢复、手工快照为 `available`、维护窗口、回切负责人和停止条件；升级失败或验收失败时恢复到 PG14 快照。
7. DC 单独授权实际升级窗口；升级后重新执行只读盘点与生产应用连通性验证。

## 实施纪律

- 新 migration 保持 PG14 兼容；如需 PG16 专有 SQL，必须先更新本决策与数据合同并得到 DC 批准。
- 当前生产 RDS 不因本决定而执行任何 DDL、DML、参数变更、快照或升级。
- PG14 与 PG16 都必须继续遵守 PostgreSQL 是正式真源、TOS 仅保存二进制、Milvus 可重建投影的边界。
